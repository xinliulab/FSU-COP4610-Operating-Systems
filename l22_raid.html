RAIDParity: one XOR block covers any one disk

    

      
a, b, c = 0b1101, 0b1100, 0b0110

      
p = a ^ b ^ c                            # parity

      
lost_b = a ^ c ^ p                       # rebuild b from the others

    

    

    
XOR: 1 if the column has
an odd number of 1s0 ⊕ 0 = 0 · 1 ⊕ 0 = 1 · 1 ⊕ 1 = 0

    
x ⊕ x = 0so a ⊕ c ⊕ (a ⊕ b ⊕ c) = b

    
$ python3 raid.py  parity: 1101 ^ 1100 ^ 0110 = 0111;  lose b: 1101 ^ 0110 ^ 0111 = 1100

    
XOR the survivors with the parity, and the lost block comes back

    
Example 1101 ⊕ 1100 ⊕ 0110 = 0111 from the earlier Lecture 22 slides · raid.py, this lecture's code, and its real output

JournalThree tricks for a faster journal

    
1 · Batch

    
write(a.txt)mkdir(lib)write(b.c)rename(x, y)

    
→

    
one Txone flush

    
Many system calls share one transactionext4 commits its journal every 5 seconds by default

    
2 · Checksum

    
TxBblkblkTxE + sum

    
Put a checksum of the transaction in the commit blockrecovery recomputes it: a torn transaction does not match and is dropped, so the commit need not wait for a separate flush

    
3 · Metadata only

    
full journaling: data written twice

    

    
metadata journaling: data once

    

    
Journal only the FAT, inodes, and bitmapsext4's default (data=ordered): write the data blocks first, then commit the metadata; the tree stays consistent, recent data may be lost

    
Real journals batch, checksum, and skip the data to stay fast

    
After Yanyan Jiang's lecture 26 ("journaling tricks") and OSTEP chapter 42 · ext4 defaults from the ext4 documentation (commit=5, data=ordered) · bars: lilac = data, teal = metadata

  

  

    

    
AppsSaving a file is harder than it looks

    

      
def save(path, data):

      
    tmp = path + '.tmp'

      
    with open(tmp, 'wb') as f:

      
        f.write(data)

      
        f.flush(); os.fsync(f.fileno())          # 1. the new data is on disk

      
    os.replace(tmp, path)                        # 2. atomic: the name points to old or new

      
    dfd = os.open(os.path.dirname(path) or '.', os.O_RDONLY)

      
    os.fsync(dfd); os.close(dfd)                 # 3. the rename itself is on disk

    

    
terminal (macOS)
$ python3 save.py
version 2 | leftover .tmp: False

    

      
how the program saves
after a crash at the wrong moment

      
open("a.txt", "w"), then write
a.txt is empty: "w" truncated it first

      
write a.txt.tmp, rename it, no fsync
a.txt can be empty: the rename reached the disk before the data

      
write, fsync, rename (save above)
the old a.txt or the new one, never a mix

ScaleKey-value stores: append now, sort later

    

      
def put(k, v):

      
    wal.append((k, v)); mem[k] = v   # one append, one memory write

      
    if len(mem) == 4: flush()

      
def flush():

      
    L0.insert(0, sorted(mem.items()))   # a sorted run, newest first

      
    mem, wal = {}, []                   # the run is now the safe copy

      
    if len(L0) == 2: compact()

      
def compact():

      
    for run in reversed(L0): merged.update(run)   # newer runs win

      
    L1 = sorted(merged.items()); L0 = []

ScaleCopies must agree: one log, five servers

    

    

      
leader, on a client command:

      
  append the entry to my log

      
  send AppendEntries to every follower

      
follower, on AppendEntries:

      
  store the entry, reply ok

      
leader, once a majority stores it:

      
  commit, apply, answer the client

      
follower, if the leader is silent:

      
  become a candidate, ask for votes

      
voter: vote yes only if the candidate's

      
  log is at least as up to date as mine
